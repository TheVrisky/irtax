# IRTAX 2.0.2 Architecture

## Confirmed decisions
- Android app version: 2.0.2 (versionCode 202).
- Independent responsive web admin dashboard for cPanel.
- Username/password accounts for app users.
- Private support conversations, visible only to the owner and authorized support staff.
- TXT upload from admin, parse, preview, approve, then convert into managed content.
- Cache downloaded articles for offline reading.
- Keep existing XML/Fragment Android base and migrate selected screens to Compose gradually.

## Repository boundaries
- app/: Android client.
- admin/: independent admin web client.
- server/: PHP API and database migrations for cPanel.
- docs/: API, deployment, security and import specifications.

## Android navigation
1. Home
2. Exams
3. Articles (existing content browser)
4. Q&A (private support)
5. Settings

Progress statistics are removed from bottom navigation. Existing favorites/bookmarks are retained within the article experience and are not deleted.

## Backend recommendation
Use PHP 8.2+ and MySQL/MariaDB on cPanel. Keep the API framework-light until hosting capabilities are confirmed (Composer, PHP version, rewrite rules, cron). API traffic must use HTTPS and JSON. Never place admin credentials, database credentials or private API secrets in the APK or browser JavaScript.

### Initial API contract
- POST /api/v1/auth/register
- POST /api/v1/auth/login
- POST /api/v1/auth/logout
- GET /api/v1/me
- GET /api/v1/articles
- GET /api/v1/articles/{id}
- GET /api/v1/infographics
- GET /api/v1/exams
- GET /api/v1/exams/{id}
- POST /api/v1/exams/{id}/attempts
- GET /api/v1/conversations/me
- GET /api/v1/conversations/{id}/messages
- POST /api/v1/conversations/{id}/messages

Admin-only endpoints live under /api/v1/admin and require server-side role checks. Every conversation request must verify ownership.

## Initial database entities
- users: username/email, password_hash, status, timestamps.
- admins: identity, password_hash, role, status.
- categories: content grouping and ordering.
- articles: title, slug, summary, status, category_id, version.
- article_sections: ordered body sections.
- infographics: title, image path, caption, publication status.
- exams, exam_questions, exam_options: exam definitions and question bank.
- exam_attempts, exam_answers: user attempts and answers.
- conversations, messages: private support threads.
- admin_activity_logs: security-sensitive admin actions.
- content_imports: TXT metadata, parse status and approval state.

Use foreign keys, indexes, UTC timestamps, prepared statements and migrations. Passwords must use PHP password_hash(). Sessions need Secure, HttpOnly and SameSite cookies, CSRF protection and login rate limiting.

## TXT import lifecycle
1. Authenticated administrator uploads TXT.
2. Server validates extension, MIME/encoding, size and permissions.
3. Parser detects headings and content blocks without assuming an undocumented source format.
4. Admin reviews and corrects the preview.
5. Admin approves the import.
6. Content is written transactionally to articles and article_sections.
7. Android clients fetch published content and update their local cache.

Parsing rules will be finalized after inspecting representative TXT samples.

## Offline strategy
- Article payloads include content version and updated_at.
- Android stores downloaded content locally and can read it without a connection.
- Sync endpoint returns changed/deleted content identifiers.
- Login, support messaging, new downloads and exam result synchronization require connectivity.
- Cached data is not overwritten by incomplete or failed responses.

## Deployment gates
Before production, confirm cPanel PHP version, MySQL version, HTTPS domain, document root, Composer availability and backups. Keep secrets outside the public web root. Test admin credentials must be changed before deployment and must never be embedded in client code.
